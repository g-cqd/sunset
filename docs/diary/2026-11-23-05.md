# 2026-11-23 — 05: Where the engine comes from without the loader's exception (roadmap 0113 A; CRIT-02)

Diary 2026-11-23-02 left one condition open: nothing in Sunset's process may load a system framework that links WebKit.

| Claim | Probe | Verdict |
|---|---|---|
| A page on the folder's engine loads no system WebKit | `webkit-preload.swift` in the probe app, a plain page, then forms, video, WebAuthn, PDF, pickers; the images before and after | **refuted**: seven of the system's WebKit images after any page. Our own WebKit soft-links AuthenticationServices, which links LinkPresentation, which links the system's WebKit |
| How many frameworks our engine may load drag the system's WebKit in | the 65 system frameworks named in our WebKit, WebCore, JavaScriptCore and WebGPU; each one's links followed (`dyld_info -linked_dylibs`) | ten: AVKit, AuthenticationServices, LinkPresentation, DataDetectors, Lookup, Reveal, VisionKitCore, PassKitUI, PassKitMacHelper, AppleMediaServicesUI. Video controls and picture in picture (AVKit) among them: not to be patched out |
| Both WebKits in one process work | the system's loaded before the page; and after it (by our WebKit itself) | before: every script "unsupported type". After: the page answers, both in the process. Not a state to ship |
| The shared cache's frameworks bind to an engine loaded first by path | the earlier probe | refuted: they bind to the cache's WebKit; only the loader's framework path changes that |
| A hardened executable reads `DYLD_FRAMEWORK_PATH` from its own load command (`LC_DYLD_ENVIRONMENT`, `-Wl,-dyld_env`) without the exception | `Scripts/probes/webkit-dyld-env.m`, Developer ID, hardened, no entitlement; LinkPresentation and AVKit loaded after | **holds**: three images of ours, none of the system's |
| The environment from outside is still ignored | the same with `DYLD_INSERT_LIBRARIES` (a team-signed library that prints when loaded) and `DYLD_FRAMEWORK_PATH=/System/Library/Frameworks` | holds: nothing inserted, the load command's folder used |
| The folder can be relative to the executable | `@executable_path/../Frameworks` | holds |
| A folder without WebKit falls back to the system's | the load command naming an empty folder | holds: the system's six images |
| It costs at launch | 40 runs each of a program linking WebKit, with and without the load command (empty folder) | no: p50 11.8 and 11.6 ms, p90 13.9 and 12.3 ms |

So the loader's exception (`allow-dyld-environment-variables`, CRIT-02) and running again (`BundledWebKit.runAgainIfNeeded`)
can go: Sunset's executable carries `DYLD_FRAMEWORK_PATH=@executable_path/../Frameworks`, a no-op for the native build,
whose `Frameworks` has no WebKit; WebKit's services get executables of ours with the same load command toward the app's
`Frameworks`. Not probed yet: whether notarization accepts the load command.

For one app with the engine as a download (0113): the load command may name a folder beside the app, where the
component is put, switched off (moved aside) or deleted; each takes effect when Sunset opens again. Two things to settle
in the ADR: the services (WebKit looks its processes up by name, so services the app ships would serve the system's
WebKit too; a patch can give ours names of their own), and the check that the engine there is the one asked for
(library validation lets any of our team's builds load).
