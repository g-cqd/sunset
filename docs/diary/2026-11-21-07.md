# 2026-11-21 — 07: WebKit's parser and DOM, looked for orders of magnitude (P1: runs of comments and text)

The owner: an audit found WebKit's handling of HTML and JavaScript "very slow by orders of magnitude in a few places". The
audit is not on this Mac; this is a search of our own. Our WebKit (base aa9b09cf67), release; Chrome Canary headless on
the same pages (its numbers are its own); `performance.now()` is coarsened to 1 ms in both.

Method: 20 kinds of markup, each parsed by `innerHTML` at n and 4n (`/tmp/n64site/stress.html`); time growing about 4 times
is linear, 16 times quadratic.

| Claim | Probe | Verdict |
|---|---|---|
| WebKit's parser is linear on misnested formatting, nested anchors, unclosed `<font>`, deep `<div>`s, unclosed `<p>`, foster parenting, many attributes, options, list items, tables, SVG, templates, long text | ratios at n = 10,000 | holds: 3.8–4.8 |
| Character references are superlinear (ratios 7.0 and 8.7 at n = 10,000) | n = 25,000, 100,000, 400,000 | refuted: 9, 36, 145 ms (named: 16, 64, 257), linear; Chrome Canary's own: 14, 58, 233 ms. The small sizes were noise |
| Sibling comments parse in linear time | ratio 15.9: 10,000 in 90 ms, 40,000 in 1,431 ms (Chrome Canary: 5 and 21 ms) | refuted: quadratic. Sampled: all in `ContainerNode::parserAppendChild`, inlined `makeChildChangeForInsertion`: `ElementTraversal::lastChild` walks back over every trailing non-element child, for each one appended |
| The same through script, and for removal | `appendChild` of comments or text: 10,000 in 85 ms, 40,000 in 1,112 ms (elements: 1 and 5 ms; Chrome Canary: 5 and 21 ms); removing 40,000 comments one by one: 1,445 ms | refuted: quadratic too (the multi-child change record; `makeChildChangeForRemoval`) |
| Only element changes need the element siblings | read: their one reader is `Style::ChildChangeInvalidation` (positional and sibling rules, `:has()` siblings, removed elements); `:empty` is checked apart | holds; a text or comment removal must also traverse no removed elements (null siblings read as "all of them") |
| Patch P1 keeps styles right | a page of 21 insertions and removals of comments, text and elements under `:first-child`, `:last-child`, `:nth-child`, `:nth-last-child`, `:empty`, `:has(+)`: computed styles at each step | holds: identical on our WebKit, the system's WebKit and Chrome Canary |
| P1 makes them linear | red: `HTMLParserSiblingRunsTests` ratios 16.9 (parse), 17.2 (text and comments), 16.2 (script append), 15.5 (removal) | holds after patches 0029–0030: 40,000 comments parse in 5 ms (was 1,431), append by script in 5 ms (was 1,112), are removed in 3 ms (was 1,445) |


Then 42 DOM and JavaScript operations at fixed sizes (`/tmp/n64site/stress2.html`), ours against Chrome Canary's own times;
most are as fast or faster here. Three are not:

| Claim | Probe | Verdict |
|---|---|---|
| Indexing a collection is constant time | `children[(i * 7919) % n]` over 20,000: 363 ms (Chrome Canary: 4.4 ms) | refuted: `CollectionIndexCache` walks from the last position; it keeps the whole list only once the count is read. Red: `DOMLinearTimeTests` growth 12.5. P2: after four scattered accesses the list is kept, as reading the count keeps it |
| `normalize()` is linear | 20,000 adjacent text nodes: 375 ms (Chrome Canary: 9.5 ms) | refuted: the first node's data grew by a copy per merged node (the code's own FIXME: the DOM spec appends once). Red: growth 12.1. P2: the data appended once; the Ranges moved first, node by node, as before (a test keeps a Range across an empty and two merged nodes) |
| P2 makes both linear, nothing else slower | after patches 0031–0032: scattered indexing 3 ms (was 363), `normalize()` 1 ms (was 375); the 42 cases again: none slower beyond noise. `normalize()` page (Ranges in merged, empty and between nodes; nesting; mutation records; selection): identical to the system's WebKit | holds. A first try crashed (a moved-from pointer read in the loop) and then lost Ranges (WebKit's merge moves them onto the previous sibling, so each merged node must go before the next is merged); both caught by the tests |
| `Array.prototype.includes` on 100,000 numbers | 200 calls: 26 ms (Chrome Canary: 1.4 ms); then per call with the result used (`/tmp/n64site/includes.html`) | refuted: 8–10 µs a call here, 7.6 µs in Chrome Canary; the first probe threw the result away, which V8 may skip. JavaScriptCore already scans Int32 arrays with SIMD (`WTF::find64`) |
