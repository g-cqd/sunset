# 2026-11-24 — 05: Why switching tabs feels slow (note n56, t298): first measurements

Release build (`swift test -c release -Xswiftc -enable-testing`, probes gated by `SUNSET_PROBE=1`, they assert nothing and print
percentiles), this Mac, 40 tabs.

| Claim | Probe | Verdict |
|---|---|---|
| The other machine's: 40 sidebar rows cost 20 ms of every switch (measured 2026-11-13, build not stated) | `TabSwitchProbe`: the real `TabSidebar` in a window, `select(item:)`, layout and display, 200 switches, fake contents | **Not reproduced in release**: p50 4.2 ms, p95 5.2 ms, max 24 ms (one outlier). The model alone: 0.01 ms. Its patch (rows as equatable views) is not needed for this size; the 20 ms was most likely a debug build. |
| Leaving a document is slow because it is pictured on the main thread at once (`setState(visible: false)` → `takePicture`) | `TabSwitchPictureProbe`, a window-sized picture, 30 runs each | Source view: p50 0.5 ms (10 sections), 2 ms (80), 6.3 ms (300): grows with the text, a part of a switch, not the cost. Rendered view: 0.07 ms at every size, **which is not credible** (the page was never laid out in the probe, so the picture is probably blank): not a measurement. |
| What the owner feels (a switch to a page or a terminal) | Not measured | The probes have no WebKit view, no Metal terminal view and no real window server: what a switch does to those is not in these numbers. |

| Signposts around a switch cost nothing when nothing reads them | `TabSwitchProbe` again, with `TabSwitchSignpost` intervals in `select(item:)`, `syncStates` (one per content, its kind asked only when read), the claim's picture, and an event in `PaneArea.body` | **Not nothing**: the model switch went from p50 0.01 ms to 0.03 ms and p95 0.01 to 0.38 ms (one run each, a busy machine); the sidebar's 4.1 ms did not move. Small beside the redraw, but it is there; it is the price of reading the real app. |
