# 2026-11-24 — 01: A vault and the keychain across an engine switch; release notes checked against the signed index

## The keychain and a vault across a switch (ADR-0125)

A test copy never touches the keychain: a named setup keeps its key in a file. To probe what the person's setup does
without his keys, `$SUNSET_PROBE_KEYCHAIN` (new) keeps a named setup's folder but its key in the keychain, under
`studio.aemi.sunset.probe-<name>`; `$SUNSET_PROBE_KEYCHAIN_ERASE` removes that key and ends (`StoragePlacesProbeTests`,
red first). Two notarized builds of one commit, served with a signed index; the native copy started with the probe.

| Claim | Probe | Verdict |
|---|---|---|
| The probe keeps the store's key in the keychain | the copy's folder after start | holds: no `storage.key`; the store sealed (`session.sealed`) |
| A vault made on System WebKit opens on Sunset's | a vault set up with a password, Touch ID off (read back as 0 before setting up); a Secure Note titled; switched to Sunset's WebKit | holds: the WebKit variant restored both tabs (the store's key read from the keychain the native wrote) and unlocked the vault with the password; the note there, kept as typed (no Done) |
| …and back | the note retitled on Sunset's WebKit; switched back to System WebKit | holds: unlocked, the new title there |
| The probe key is removed | the eraser, then a build that can read the item | holds: `existed: false` after removal. Without the probe variable the eraser refuses (exit 64) |

On the way: typing into secure fields with key events doubled the text ("The two passwords are not the same."); the values
were set through accessibility instead.
