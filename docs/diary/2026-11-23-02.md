# 2026-11-23 — 02: One app, its WebKit a component (roadmap 0113 step A)

Can one process run on a WebKit chosen at run time, kept outside the app, without the loader's variables and the
`allow-dyld-environment-variables` exception (the outside audit's CRIT-02)? Probes: `Scripts/probes/webkit-preload.swift`
(a host that does not link WebKit, loads the frameworks of a folder leaves first, then loads system frameworks and a page)
and `Scripts/probes/webkit-service-shim.c` (WebKit's services with their executable replaced: load the folder's frameworks,
then `WKXPCServiceMain`, the only symbol WebKit's own service executables use). The engine: the frameworks of the installed
Sunset WebKit (signed by our team, notarized with that app), copied to `/tmp`. macOS 27.2.1.

| Claim | Probe | Verdict |
|---|---|---|
| Frameworks loaded by path, leaves first, bind to each other and not to the system's | the host, its WebKit images listed | holds: only the folder's seven images |
| Later loads of the system's WebKit path bind to the one loaded | `dlopen` of `/System/Library/Frameworks/WebKit.framework/WebKit` | holds: none of the system's (dyld matches the install name) |
| Every framework Sunset links binds to it too | the 27 frameworks of Sunset's executable, loaded after | holds: none of the system's |
| System frameworks that link WebKit bind to it too | SafariServices, LinkPresentation, AuthenticationServices, QuickLookUI, Quartz, PassKit, ContactsUI, SharingUI | **refuted**: from the shared cache, they bring the system's WebKit, WebCore, JavaScriptCore and four more (seven images). PDFKit, StoreKit, MapKit, ShareKit do not |
| A page runs with both WebKits in the process | LinkPresentation and SafariServices loaded, then a page | **refuted**: no service started, evaluation failed ("unsupported type") |
| A tool without a bundle finds WebKit's services | the bare host | refuted: `bootstrap look-up … No such process`; services are found only in an app's `Contents/XPCServices` |
| Services that do not link WebKit run on the folder's engine | a probe app: the host, the three shims as `Contents/XPCServices` | holds: the page answers; networking, GPU and web content each on the `/tmp` WebKit and WebCore (`lsof`) |
| …hardened, Developer ID, library validation on, no loader exception | the same, signed so | holds |
| Library validation refuses an engine not ours | the engine's WebKit signed ad hoc | holds: `dlopen` refused (code signature) |
| A quarantined engine loads | quarantine on every file of the copy | holds for this one (notarized within its app). Not probed: one never notarized |

So: a downloaded engine is possible without the loader exception, if (1) Sunset's executable links no WebKit (the code
that imports WebKit in a library loaded after the engine), (2) the app ships its own small service executables, loading the
engine and calling `WKXPCServiceMain`, and (3) nothing in Sunset's process ever loads a system framework that links WebKit.
(3) is not in our hands alone: WebKit and AppKit load some on demand (sharing, Quick Look, password AutoFill). Each needs a
probe in the app; a watch on the images loaded (`_dyld_register_func_for_add_image`) can say so when one comes.

Not settled here: the engine is in a folder the person's programs can write. Library validation lets only our team's
builds load, an older one included: the app must check the engine's version (as `refuseOtherWebKit` does now) against what
it was told to download.
