# 2026-11-23 — 08: WebKit's processes under names of ours (roadmap 0113 B; ADR-0124)

WebKit finds its processes by name (`com.apple.WebKit.WebContent`, `ProcessLauncherCocoa.mm`), and an app's own services
of those names come first. One app that can run on either WebKit would hand the system's WebKit our services, without
Apple's entitlements (ADR-0124).

| Claim | Probe | Verdict |
|---|---|---|
| A patch can let the app choose the names looked up | patch 0037: `WebKitXPCServicePrefix` in the app's Info.plist takes the place of `com.apple.WebKit` in the name given to `xpc_connection_create`; the service is still told WebKit's name; a service's sandbox profile is the one of the name its Info.plist says (`WebKitServiceName`), not of its bundle identifier | builds (the first build: `dynamic_objc_cast` not declared in `AuxiliaryProcessMac.mm`; a plain class check instead); 209 s incremental |
| Sunset WebKit runs with its services under our names | `make-webkit-app.sh`: services `studio.aemi.sunset.engine.*`, each with `WebKitServiceName`, signed with WebKit's identifier; the test copy started in the background on example.com | holds: networking, GPU and web content started from `studio.aemi.sunset.engine.*.xpc`, each on our WebKit, each sandboxed (`sandbox_check`); none of the system's WebKit in Sunset |
| The system's WebKit ignores services under our names | the native test copy with those services added to its bundle, signed again | holds: no process from the app's services; the system's own web content process started for the page |
| The series still passes its tests | `Scripts/webkit.sh test` | 600 API tests passed (the 23 known extension failures), the 453 layout tests as expected; one unexpected: `DOMLinearTimeTests/collectionIndexedAtScatteredPositionsInLinearTime` (ours, patch 0031), which then failed 2 runs of 3 alone with a ratio over 8: a timing test on 5 000 children in the page, untouched by 0037 (which names services). Flaky; to be made sturdier (more children, the best of several runs) |
