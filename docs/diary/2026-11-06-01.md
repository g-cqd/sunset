## Memory and idle cost (owner notes n11 and "memory and cpu usage appears to be very big")

Measured with the competitor harness (`bench/idle.sh sunset`, now with a Sunset case and an app option `--scrollback`; 100 000 lines of history like the others). First numbers, 0 lines: 118 MB, 486 M instructions/s, 62 wakeups/s; after 1M lines: 926 MB (peak 942), 1660 M instructions/s. The others: 63-134 MB at 0 lines, 0.04-5.7 M instructions/s idle, 0.3-15 wakeups/s; 81-470 MB after 1M lines.

Causes found by sampling, `vmmap` and a benchmark (not by guessing):
1. **Snapshots copied the whole history.** `takeSnapshot` returns a copy of the screen; the history was one flat array, so after each snapshot the next written line copied it (up to 100 000 lines). Benchmark `terminal/flood with a snapshot per read`: 2387 M instructions and 385 ms per MiB against 57 M for the same bytes with no snapshot (42x). Fix: the history is stored in chunks of 128 lines (`Scrollback`), a copy shares them, a write copies only the newest chunk, the oldest chunk is released when its lines are gone (storage is limit + one chunk) and recycled (the rolling `terminal/ascii` benchmark is back at 0 mallocs, 58 M). After: 75 M instructions, 12 ms per MiB (30x less), tests first (7 storage tests: order across wraps, bound, sharing).
2. **Every blink phase redrew the whole screen** (29 M instructions twice a second even at an idle prompt) because the text-blink phase flipped with the cursor phase. Now only rows that were drawn with blinking text are redrawn on a phase change (5 tests, first red: all rows were drawn).

Result (same harness, same machine, load 15): after 1M lines 291 MB (peak 307), was 926 (peak 942). Idle: 337 M instructions/s (was 486), 39 wakeups/s (was 62). Idle is still 60-100x the other terminals: what is left is presenting (each blink makes the whole 2460x1650 image: a 16 MB byte array, a 16 MB `Data` copy, a CGImage and Core Graphics' colour conversion on the CPU, seen as vImage in the samples) and wakeups that I have not traced.

## Throughput, second cut: the reader no longer waits for the parse

The vtebench numbers above were taken at load 16-24 and are mostly the machine's load (every thread hop waits for a CPU). Repeated at load 4 (`bench/results/2026-11-06/`, same harness, one run each, 10 samples, windows visible), the pipeline before this change: scrolling 62 ms, dense_cells 24, medium_cells 24, unicode 30.

Cause (reasoned from the code and the 5 s samples, then confirmed by the numbers below): the pseudo-terminal hands out about 1.3 KiB per read (measured: 4 MB in 3154 reads). Each read was a task on the reader thread, a pipe write to wake that thread, a hop to the session actor, the parse, and only then the next read: nobody read while the parse ran, and every kilobyte cost several thread switches. Also each read allocated and zeroed 64 KiB.

Now `OutputPump` (SunsetHost): one long task on the reader thread polls and reads continuously into a buffer (one 128 KiB read buffer, allocated once); the session takes what arrived as one batch (up to 256 KiB) and yields to the actor's other work between batches. The reader stops at 1 MiB waiting (the child is then slowed by the kernel's buffer) and a `take` restarts it; no timeouts, no wakeups when idle. Tests (4, written first; the stub hung, the real one passes): order and completeness for 5000 lines, coalescing while the consumer is busy (under 200 batches for 4 MB), the limit holds and nothing is lost, no wakeups idle and stop in under 100 ms.

Same load (about 4), medians in ms, Sunset before / after, then alacritty and ghostty measured in the same minutes:

## The renderer's pixel loops (found while checking the "GPU?" question)

Measured with a real font at retina size (JetBrains Mono, cells of 17x37 pixels, 120x40, surface 2040x1480): one full CPU frame took **24 ms** with the per-cell path (12 ms with ligature runs on), of which a *blank* screen was already **8 ms** (the fills alone). The C probe of the same fill runs at 59 GB/s (5 us per strip), so the Swift `fill` was ~80x off: `surface.pixels[i] = color` pays a uniqueness check and a bounds check per pixel, and `blit` did bounds guards per pixel too. The earlier "kernel" list (and the owner's remark that there are more opportunities than I said) was wrong to treat fills as solved: the C compiler vectorises them, the Swift code did not.

New benchmarks (`render/retina full frame, blank|text`, synthetic antialiased glyphs: 60 % empty, 15 % solid, the rest mixed): blank 58 M instructions, 6.8 ms; text 125 M, 18 ms. After: `fill` takes the buffer once and stores a row at a time (`update(repeating:)`), `blit` clips the bitmap to the cell and surface once and walks rows with pointers: blank **5.0 M (11.7x), 0.56 ms**; text **27 M (4.6x), 2.3 ms**. Pixel output identical (the 78 render tests, which compare exact pixels, pass; the blend formula is unchanged). The remaining text cost is the blend itself (probe: NEON 5.3x over scalar, exact) and the per-cell logic.

### NEON blend (C target `CSunsetKernels`), and what it did and did not do

`CSunsetKernels` (new C target: `sunset_blend_coverage` with NEON, `sunset_blend_coverage_scalar` as the reference and the non-ARM fallback), used by `blit` through `PixelKernels`. The tests (written first; the stub failed them) compare the vector kernel and the scalar one with the exact formula `(c*a + d*(255-a) + 127)/255` in plain Swift for every length 0-70 at four alignments and for all 256 coverage values: bit-identical. The glyph row tail (a 13-pixel row is 8 + 5) is done as a padded vector step (probe `probes/blend-tail.c`: 390 ns per 13x29 glyph, against 467 ns with a scalar tail and 413 ns with an overlapped masked tail; all three give identical pixels).

Effect, honestly: the first version of `fill`/`blit` in Swift took the text frame from 125 M to 27 M instructions; the NEON blend then took the *instructions* from 27 M to 22 M (with the scalar tail) and 27 M with the padded tail (more instructions, fewer cycles: instructions are not the right gate for vector code). Wall time on this machine is useless today (load 15-19 from other builds). In a spin of full text frames with the synthetic glyphs the frame cost fell from about 18-24 ms (before this session's renderer work) to about 2 ms in the quiet runs, and the profile of the 22 M version still showed the blend at about half of the frame (scalar tail 854 + vector 422 samples against 300 each for `drawRow`, `render`, `drawCell`). Next in the renderer: the per-cell work (`drawCell` copies the screen's palette and style per cell), and not drawing rows that did not change in a full-screen flood.

## The wheel never scrolled the history (owner: "i can't scroll")

Cause: `report` in `TerminalNSView+Mouse` passed `event.clickCount` to the model for every pointer event. `NSEvent.clickCount` is only valid for mouse button events; on a scroll-wheel event it raises an Objective-C exception, which AppKit swallows, so `report` ended before `model.pointer` and the wheel never reached the history scrolling (found by logging each step: `WHEEL` and `REPORT wheelUp` were printed, `POINTER` never). It has been broken since the mouse commit (`a7f6e15`); I had only tested the keyboard (Shift+Page) path in a window, never the wheel. Fix: the click count is taken only from button events (0 otherwise). Checked in the app with synthetic line-unit wheel events (4 events of 5 lines moved the window from lines 283-300 to 258-276 of 300); a real trackpad (precise deltas, momentum) was not tried by me. No unit test: the failure needs a real `NSEvent` in a window.

## Wheel inertia and the terminal card (owner notes, 2026-11-07)

**Scroll inertia.** Owner: "i don't think you set up inertia for the scroll". Right for a wheel; not for a trackpad. Apple docs (`NSEvent.momentumPhase`, `phase`, `hasPreciseScrollingDeltas`): a trackpad or Magic Mouse sends its own stream of momentum events after a flick (they stop when a finger touches down), which `ScrollAccumulator` already turned into lines; a wheel sends whole notches and no momentum, so each notch jumped 3 lines at once. New: `ScrollMomentum` (SunsetCore, pure, 7 tests red first): a notch becomes a speed `lines / timeConstant` that decays exponentially, so the distance is exactly what the notch asked for and only its timing changes; more notches add speed, the other direction brakes, a key press stops it; frame-rate independent (30 vs 144 Hz differ by at most one line, tested). `TerminalNSView+Scroll` steps it from a display link that exists only while the text glides. New key `scroll.inertia` (seconds, 0 turns it off, default 0.2, Settings > Scrolling). Found by the live check and fixed red first: the last fraction of a line was lost at rest (a 3-line notch scrolled 2); it is now rounded in at rest. Measured with one synthetic 3-line notch posted to the running app: inertia 0.2 gives lines at 0, 150, 600 ms; 0.6 gives 0, 417, 1133 ms; 0 gives all 3 at 0 ms. **Not verified:** how it feels with a real wheel or a real trackpad flick (only synthetic events), that a finger landing cancels our wheel glide (it does not need to: a precise event stops it by code, untested live), pixel-smooth scrolling (the grid scrolls by whole lines; a sub-line offset needs the renderer to draw a shifted grid: not done).

**Terminal card.** Owner: padding without the sidebar must still be filled by the terminal's background edge to edge; with the sidebar, the outer space is the window's colour (not the terminal's), the terminal is rounded and has a thin stroke. Done: `window.padding` is always inside the terminal (the grid's inset, its background fills it); with the sidebar, `TerminalCard` insets the terminal by `sidebar.padding` (2-4 pt), clips it to a continuous rounded rectangle (`sidebar.cornerRadius`, default 8, 0-24) and draws a 0.5 pt stroke at 12 % of the label colour; the root colour is `windowBackgroundColor` when opaque (a window material shows through otherwise). Screenshots checked: no sidebar, padding 12 and a blue background fills the window to its edges; sidebar on, rounded card with window colour around it. The 8 pt margin of the owner's layout sketch conflicts with the earlier "2-4 pt" rule; kept 2-4 until told otherwise.

## Window corner radius, concentric card, custom sidebar, edge-to-edge background (owner notes, 2026-11-07)

**The window's corner radius, measured two ways (macOS 27.0.1).** (1) AppKit: the window's frame view (`NSThemeFrame`) answers `_cornerRadius`: 16 for a titled window, with or without `fullSizeContentView` and with a toolbar, 0 for a borderless one (small probe program, then a test: `WindowCornerRadiusTests`). (2) From pixels: `screencapture -o -l <window>` keeps the alpha channel; the mask of TextEdit's window, our native-title-bar window and our no-title-bar window give the same profile, which fits a circle of 17 pt (edge reaches 0 at 18 pt): the corner is continuous (a squircle), so a circle fit reads about 1 pt more than the nominal 16. Public API: macOS 27 has `NSViewCornerConfiguration` / `effectiveCornerRadii` and SwiftUI has `ConcentricRectangle` + `containerShape`, but they take a container shape *you* give; nothing public reads the window's radius, so `SunsetPrivate.WindowCornerRadius` asks the frame view (name decoded by InternedStrings, nil if it stops answering, fallback 16). `ConcentricRadius.inner(outer:inset:)` (SunsetHost, 3 tests red first) = radius minus margin, never below 0.

**Card.** With the sidebar the terminal is inset by `sidebar.padding` (now 0-16, default **8**, as in the owner's layout sketch; the earlier "2-4 pt" rule is replaced) and clipped to a continuous rounded rectangle of radius 16 - 8 = 8, a 0.5 pt stroke on it. The `sidebar.cornerRadius` key added a day earlier is removed: the radius follows the window's. Measured in a screenshot: margins 8 pt (right, top, bottom), card corner fits 8.5 pt against the window's 17 fitted (same bias): concentric. The grid has at least 6 pt inside the card so that rounded corners do not cut text.

**Sidebar.** Not a `List` any more: a `ScrollView` of `SidebarRow`s (8 pt padding, 8 pt rounded highlight, hover and selected variants, dimmer when the window is inactive, title cut with "…", a 24 x 24 close button while hovered), nothing else in it (the "New Tab" footer is gone). No background by default (`sidebar.material` defaults to `transparent`; the window's colour or material shows; the option stays). Its first row starts below the traffic lights (their `y` + 14 pt + margin) and content scrolled up under them fades out (a gradient mask: `scrollEdgeEffectStyle` only acts against pinned content such as a toolbar, which the AppKit traffic lights are not). A strip on its trailing edge resizes it (`sidebar.width`, 120-480). Screenshot checked: rows, selection highlight, no background, card. **Not verified (mouse):** hover highlight, the close button, drag to resize, drag to reorder, the fade while scrolling a long list.

**The background reaches the edges.** The surface was sized to whole cells, so up to a cell of the view (right and below) showed black instead of the terminal's colour, in every layout. `FrameView.extraWidth/extraHeight` make the surface cover the whole view and the renderer paints the leftover with the background (2 tests red first; seen in the screenshot: the black strip under the terminal is gone).
